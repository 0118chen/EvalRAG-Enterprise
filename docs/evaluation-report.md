# 法规问答检索评测报告（2026-09-27）

固定语料、固定题集、六组检索配置的实测结果。所有数字来自本仓库自己的检索与评测链路
（`app/core/retrieval_service.py` + `app/core/evaluation_runner.py`），可由
`scripts/run_golden_experiment.py` 一键复跑。

**本版数字对应 18 份语料（386 chunk，2026-09-27 扩容后）**。当前口径是 **11 组检索配置**的
融合矩阵：`docs/evaluation/golden-set-{v1,v2,v3}-fusion-2026-09-28.json`（含加权/截断/分数式
三种融合修法的对照，融合机制归因见 **§11**）。语义重排（TypeSafe）那一轮是独立产物
`docs/evaluation/golden-set-{v2,v3}-typesafe-2026-09-28.json`，因为它是付费调用、不能进离线矩阵。
此前各轮的产物也都在仓库里：6 组配置的 18 份语料轮
（`golden-set-v{1,2}-corpus18-2026-09-27.json`）、13 份语料轮
（`golden-set-2026-09-27.json` / `golden-set-v2-2026-09-27.json`，两轮对照见 **§9**）。

## 0. 一句话结论

**v1 的指标饱和主要来自题集，不是系统。** 52 道题的证据引文 100% 落在标注页码上，标注可信；
但在 18 份语料上**纯 BM25 就已经是文档级/页级满分**（Recall@1 = 1.000、MRR = 1.000、page_hit = 1.000），
重排的增益因此归零。去掉"问题里写出制度全称"这一词面泄漏、并把措辞也改写成日常说法之后（§8 的 v2 题集），
同一套检索链路的 Recall@1 是 **0.660**、page_hit **0.851**——**约 34 个百分点来自题集的词面重合**。

其他可复现的结论：

1. 本地 hash 向量（32 维）构成的 dense 通道质量远低于 BM25（单跳题页级第一 7/52 与 2/20，
   而 BM25 是 35/52 与 16/20），把它按等权 RRF 融合进去会**拉低**结果
   （v2：BM25 0.660 → 融合 0.527，融合+重排 0.546）。负优化已定位到三处机制——等权投票、
   只用名次丢分数、弱通道与强通道的错误高度相关——其中前两处可以修：**分数式 + 加权后，
   v3 上混合检索首次超过纯 BM25（0.850 vs 0.800、page 0.950 vs 0.900）**，v2 上仍差 1 道单跳题（§11）；
2. 单次检索 p50 0.48–1.32 s（386 chunk，缓存未命中），瓶颈仍是每查询重建检索器并把整个语料重新嵌入
   ——`sparse` 与 `dense` 的 `embed()` 调用次数**完全相同**（每查询 387 次），说明"只做 BM25"也在为全语料嵌入付费；
3. 重排的收益在简单题集上已经归零（v1 在 18 份语料上 +0.0 pp，13 份语料时是 +1.9 pp），
   在难集上只剩"hybrid 组 +3.4 pp"，补不回与纯 BM25 的 11.4 pp 差距；
4. 8 道应拒答负样本**全部**检索到了内容，且 top 分数与正常问题重叠——单纯靠分数阈值拒答会误杀约 10% 的正常问题；
5. 语料从 13 份扩到 18 份（316 → 386 chunk）**没有降低召回**：纯 BM25 在 v1 上仍是 1.000、在 v2 上 R@1 逐位不变，
   被稀释的是弱通道（dense R@1 −4.5 pp、hybrid R@1 −2.0 pp）——逐题归因见 §9。
6. **把弱通道换成真语义通道（TypeSafe / Jev）才是决定性的**：同一个融合候选集上，
   v2 的 R@1 0.646 → **0.769**（单跳 37/52 → 45/52）、v3 0.850 → **0.950**，page/passage 指标
   同时超过纯 BM25。代价是每查询 +1.8s、按输入 token 付费（v2 全量 $0.0697）且候选正文出网，
   因此它是默认关闭的可选后端；多跳题一道没涨（0.500 → 0.500），因为重排改不了候选集（§11.5）。
7. 顺带查出一个**不可复现缺陷**：融合的平局胜负原本由"谁先被传进去"决定，而候选顺序又来自
   `order_by(chunk_id)`、chunk id 前缀是每次导入重新生成的 UUID——同一份语料、同一套题，
   v3 的等权 RRF 跑出过 0.550 与 0.700 两个值。破平已改为只用内容，并加了"调换 id 顺序结果不变"
   的回归与"两次独立导入逐位相同"的可复现性检查（§11.4）。

## 2. 方法

```bash
# 导入 law/ 下 18 份文件（走生产同一条 worker 函数），重建数据库与题集，跑六组配置
python -m scripts.run_golden_experiment \
    --json docs/evaluation/golden-set-v1-corpus18-2026-09-27.json \
    --markdown docs/evaluation/golden-set-v1-corpus18-2026-09-27.md
# 延迟归因（可选）
python -m scripts.profile_retrieval --database data/experiments/golden.db --tenant golden-experiment
# 饱和成因探针（可选）：引文排名分布 + 去掉法规名的对照
python -m scripts.probe_golden_difficulty --database data/experiments/golden.db --tenant golden-experiment
```

- **语料**：18 份法规（10 PDF + 5 DOCX + 2 HTML + 1 XLSX），386 chunk / 245,740 字符，版本 `latest`，单租户。
- **题集**：52 题，`top_k=5`，每题单文档单页。
- **嵌入**：`EMBEDDING_PROVIDER=hash`（32 维），`DENSE_RETRIEVAL_BACKEND=local`、
  `SPARSE_RETRIEVAL_BACKEND=local`——**没有接外部向量库/ES**，也没有用外部 embedding API。
- **缓存关闭**（`CACHE_ENABLED=false`）：保证每题都真正走一次检索，延迟即"缓存未命中"的延迟。
- **无外部付费调用**：重排是词面 `LexicalReranker`，查询改写是规则表 `RuleBasedQueryRewriter`
  （`app/core/query_rewrite.py`），全程确定性、可重复。
- **指标口径**：`Recall@k`/`MRR`/`nDCG@k`/`precision@k` 为**文档级**（`app/core/evaluation.py`）；
  `page_hit` = top-5 里存在 (期望文档, 期望页码) 的 chunk；
  `passage_hit`/`passage_at_1`/`passage_mrr` = 证据引文是否被检索到、是否排第一、倒数排名（平台内计算，
  需要样例带 `evidence_quote`）；
  另有脚本侧独立实现的 `quote_hit` 作为交叉校验，两者逐位一致。
- **可复核性**：结果 JSON 里每题一行（`per_example`：问题、类别、来源文件、recall@1/@5、page_hit、
  quote_hit、`passage_rank`、延迟、命中 chunk 的文档/页码/分数），所以下表任何汇总数字都能回查到具体是哪几道题。

**随机基线**（同样 top-5、从 386 chunk 里随机抽，按每题相关 chunk 数精确计算，非估计；
扩容让随机基线自己降了：分母从 316 变 386）：

| 指标 | 随机 | BM25 |
|---|---|---|
| 文档命中 | 0.214 | 1.000（Recall@1） |
| 页命中 | 0.142 | 1.000 |

所以这套题**不是**随机可解的；它的问题是"太容易"，不是"无意义"。

## 4. 五个发现

### F1 dense 通道本身就是噪声源，hybrid 因此比 BM25 更差

dense-only（R@1 0.673）和 BM25（R@1 1.000）差距巨大，而两者的等权 RRF 融合（R@1 0.904）
落在中间且**低于** BM25。逐题对照更直接，按"quote 与 page 都命中"作为完全正确
（BM25+重排 50/52 完全正确，产品默认 44/52）：

| 对照 | 完全正确的题数 |
|---|---|
| BM25 + 重排 胜过 产品默认（默认丢、sparse 中） | **6** |
| 产品默认 胜过 BM25 + 重排 | **0** |

即 BM25+重排在这套题上**严格优于**当前默认的 hybrid 配置，且没有任何反向案例。被拖累的 6 题：

| 题目 | dense-only | BM25+重排 | 产品默认 |
|---|---|---|---|
| 《流动资金贷款管理办法》贷款期限规定 | 丢 | 中 | 只中页码，丢引文 |
| 商业银行破产清算优先支付 | 丢 | 中 | 只中页码，丢引文 |
| 《流动资金贷款管理办法》贷款人违规经营应被采取什么措施 | 丢 | 中 | 全丢 |
| 《个人贷款管理办法》"银行业金融机构"定义 | 丢 | 中 | 中引文，丢页码 |
| 民法典：监护人的责任 | 只中页码 | 中 | 只中页码，丢引文 |
| 《农户贷款管理办法》无法收回的贷款如何处理 | 丢 | 中 | 全丢 |

全量引文级漏检：sparse+重排 2/52、产品默认 7/52、dense-only 20/52；
页级漏检：sparse+重排 0/52、产品默认 3/52、dense-only 12/52。

根因：`EMBEDDING_PROVIDER=hash` 是 32 维哈希词袋，只有词面信息且维度过低，
它排出来的名次被 RRF 当成与 BM25 同等可信的一票。**修法不是调 RRF 权重，而是换真正的语义向量**——
在拿到 embedding API key 之前，仓库里不应该声称 hybrid 优于 BM25。

### F2 重排唯一补上的那道题，被"多加 5 份文档"自己补上了

13 份语料时 BM25 的 R@1 是 0.981 → 加词面重排 1.000，且唯一被改动的就是
**《中华人民共和国农村集体经济组织法》自何时起施行？**——期望文档由第 2 位提到第 1 位
（该题答段在两版里都排第 4，passage@1 不变）。
扩容到 18 份后，**纯 BM25 自己就把这道题排到了第 1 位**（逐题对照只有这 1/52 道题变了），
于是重排增益变成 +0.0 pp，`passage_rank` 52 题一个都没变。

能解释的原因是 BM25 的统计量随语料变：新增 5 份文档改变了词项的文档频率与平均文档长度，
原来第 1、2 名之间的分数差随之翻转。**这说明"重排 +1.9 pp"不是重排的稳定能力，
而是特定语料规模下的排序巧合**——写进简历必须带上语料规模这个前提。
延迟差异在噪声范围内（同一脚本四次重跑 p50 波动约 ±5%），词面重排的代价可以忽略；
但同一套重排在 hybrid 上只能从 0.904 补到 0.942，仍补不回 dense 造成的损伤。

### F3 指标饱和，这套题集无法区分配置——两个成因都已量化

BM25+重排在 Recall@1/3/5、MRR、nDCG@3/5、page_hit 上全为 1.000。
继续做检索层"优化"在这个语料上**无法被验证**。饱和不是单一原因，用
`scripts/probe_golden_difficulty.py`（同一脚本可复跑）测出两个来源：

**成因一：文档级指标在 13 份文档上太粗（差异被聚合吃掉）。**
把"证据引文所在 chunk 的排名"单独统计，同一批检索结果里的差距立刻显现
（下表来自 `scripts/probe_golden_difficulty.py`，与平台内 `passage@1` 指标逐位一致）：

| 配置 | 引文排第 1 | 第 2–5 | 不在 top-5 | passage@1 |
|---|---|---|---|---|
| sparse-bm25 | 40 | 10 | 2 | 0.769 |
| sparse-bm25-rerank | 40 | 10 | 2 | 0.769 |
| hybrid-rrf-rerank | 33 | 11 | 8 | 0.635 |
| hybrid-rrf-rerank-rewrite | 32 | 13 | 7 | 0.615 |
| hybrid-rrf | 27 | 15 | 10 | 0.519 |
| dense-hash | 14 | 18 | 20 | 0.269 |

文档级全是 1.000/0.94 的时候，passage@1 的差距是 0.769 : 0.269。
语料只有 18 份文档、每份约 21 chunk（占语料 5.6%），随机抽 5 个 chunk 就有 0.214 的文档命中率，
"命中文档"本身是个廉价事件。另外注意 `sparse-bm25` 与 `sparse-bm25-rerank` 的 passage@1 相同（0.769），
说明重排修的是文档级 rank-1 的那一题，并没有改变"答段是否排在第一"。

**成因二：提问点名法规，而法规全称在原文里逐字出现。**
49/52 的提问含《…》法规全称，等于给 BM25 一条近乎唯一的词面线索。把《…》整段去掉后重跑同一套检索：

| 变体 | R@1 | R@3 | R@5 | MRR | page_hit | quote_hit |
|---|---|---|---|---|---|---|
| 原始提问 | 1.000 | 1.000 | 1.000 | 1.000 | 1.000 | 0.962 |
| 去掉法规名 | 0.885 | 0.942 | 0.981 | 0.919 | 0.981 | 0.962 |

即 **11.5 个百分点的 Recall@1 来自"问题里报了法规名"**。`quote_hit` 不变说明摘掉标题后 BM25 仍能找回那段话，
掉的是排序；同时重排的增益完全消失（去掉标题后 rerank 开关对结果零影响），
说明它原先补的那道题正是靠标题词面拉平的。

**第三层偏置（本批数据无法证伪，但方向明确）**：题集由 LLM 从原文起草且强制"引文必须在所标页面逐字找到"，
因此问题措辞贴近原文用词，且全部是单文档、单页、单跳、必有答案，没有同义改写、跨文档多跳或应拒答的负样本。
唯一的三道近邻干扰题（三份文件"贷款人"定义逐字相同）恰好是默认配置丢分的地方。

**顺序**：先修指标口径（把 passage 级指标做进产品），再修题集难度——否则改完题集也没有可比的基线。

### F4 单次检索 p50 0.69–1.14 s，全是可消除的重复计算

用配置之间的差值可以把延迟拆开（数据来自上表，属推断而非微基准）：

| 环节 | 实测依据 | 量级 |
|---|---|---|
| 全语料嵌入（386 chunk）+ 余弦 | dense-only p50 484 ms（只做这一件事） | ~480 ms |
| BM25 打分（含对全语料重新分词） | sparse p50 775 ms − dense 484 ms | ~290 ms |
| 两者叠加 | hybrid p50 1277 ms ≈ 2×484 + 290 | ~1260 ms |

`scripts/profile_retrieval.py` 的 cProfile 佐证：`hybrid` 每查询调用 `embed()` 774 次
（= 386 chunk × 2，实测 3 轮 2322 次），而 `sparse` 也调用了 **387 次**（实测 1161 次）——
**"只做 BM25"的配置和 dense 的嵌入开销只差一个查询向量**，这正是 F5 第 1 条的直接证据。
改写触发时（p95 2574 ms）翻到每查询 1548 次（实测 4644 次）。

### F5 三条代码级原因（第 2 步的具体工作项）

1. **`retrieve()` 在 mode 分支之前无条件算两个通道**（`app/core/retrieval.py:88-107`）：
   dense 分数算完、排序完，才在最后判断 `mode == "sparse"` 并把它丢掉。
   所以"只做 BM25"的配置也在为全语料嵌入付费——**这也是 sparse(775 ms) 比 dense-only(484 ms) 更慢的原因**
   （profiler 实测两者 `embed()` 调用次数完全相同）。
2. **检索器每查询重建**：`RetrievalService._build_retriever()` 按查询调用 `create_retriever()`，
   每次都新建 `LocalRetriever` 并对全语料重新分词/嵌入。BM25 应当是建库时算好的倒排索引 + 文档长度统计。
3. **`HybridRetriever` 组合两个 `LocalRetriever`**，而每个 `LocalRetriever` 内部又会走完整的 `retrieve()`，
   于是同一份语料被嵌入两遍、BM25 也被算两遍（`app/core/backends.py:73-89`）。

粗算修完第 1、3 条后的量级：sparse 775 → ~290 ms，hybrid 1277 → ~775 ms。
这是**基于实测分解的推断**，第 2 步落地后必须重新测量，不能直接写进简历。

## 6. 已知局限

- 未接真实 embedding 模型、未接真实 Milvus/ES，全部为本地后端；hybrid 的结论**只对 hash 向量成立**。
- 文档级指标在 18 份文档、每份约 21 chunk（386 chunk）的规模下区分度有限；`quote_hit` 是本报告自加的补充指标。
- 证据引文用严格子串匹配，chunk 为 800 字窗口。已核对：BM25+重排剩下的 2 次漏检**不是**窗口切断造成的
  ——引文（35 字、65 字）完整落在语料内单个 chunk 里，只是那个 chunk 没进 top-5，属真实排序失误。
- 延迟为单机 Windows + SQLite + 缓存关闭下的串行测量，不是并发压测结果（同一脚本四次重跑，p50 波动约 ±5%，
  并发跑测试时会被推高到 820 ms）；质量指标可复现（四次重跑逐位相同），
  且平台内的 passage 指标与脚本侧独立实现完全一致（结果 JSON 的 `passage_cross_check` 全为 true）。

所以"去泄漏"主要由同义改写这一类承担；多跳和等价是**标签形态**的扩展，不是难度的扩展。

不静默丢弃——例如"两跳来自同一侧"出现 3 次，说明跨文档题并不是随便就能造出来。
（多跳题多为"两问合一"的长问句，不是真正的组合推理，算标签能力而不是难度提升——

### 8.3 四条结论

1. **v1 的高分主要是题集的词面泄漏，不是检索做得好。** 纯 BM25 的 Recall@1 从 1.000 掉到 0.660
   （**−34.0 pp**；13 份语料时是 0.981 → 0.660，−32.1 pp）、page_hit 1.000 → 0.851、passage@1 0.769 → 0.612。
   注意上一轮"只把法规名从问题里去掉"的对照只值约 11.5 pp——两者不能相加：
   那次只拆掉了"首页出现制度全称"这一条线索，而 v2 连**措辞**也改成了日常说法
   （词面重合中位数 0.429 → 0.333）。合起来的 32 pp 才是"题集给检索器的全部便宜"。
   这也意味着：**在这套语料上 BM25 的真实水平是 0.66 左右**，之前写进任何文档的 0.98/1.00 都不可迁移。
2. **重排的收益随难度归零（在扩容后的语料上，连简单集也归零了）。** v1 上 BM25+重排 1.000 → 1.000
   （+0.0 pp；13 份语料时是 +1.9 pp，那道题被 BM25 自己补上了，见 §4 F2），
   v2 上是 0.660 → 0.660（+0.0 pp，只有 R@3 +0.8 pp）。只有 v2 的 hybrid 组还留着 +3.4 pp
   （0.512 → 0.546），但仍比纯 BM25 低 11.4 pp。
   原因可以指到题：重排在 v1 上总共改变了两道题，其中唯一改变 R@1 的那道是
   **"《中华人民共和国农村集体经济组织法》自何时起施行？"**——一道题面就把答案文档名报出来的题。
   同一种词面信号重排一遍，修不了词面信号本身的漏召。
3. **hybrid 依然低于纯 BM25，且差距更大**（v2：0.512 vs 0.660，−14.8 pp，融合+重排 0.546 / −11.4 pp；
   v1：0.904 vs 1.000，−9.6 pp）。在 v2 的 by-category 里，同义改写 R@3 0.827、多跳 0.889、等价多标签 0.639。
   结论方向与 F1 一致：本地 32 维 hash 向量无语义，等权 RRF 把噪声搬进了融合结果。
   这不构成"混合检索不好"的结论——只对 hash 向量成立。
4. **应拒答：现有策略完全无效，而"加个分数阈值"已被数据否掉。**
   8 道负样本 `negative_retrieved_rate` = **1.000**（全部检索到了内容）。
   在**纯 BM25** 这一组上，负样本的 top 分数是 22.7–84.8，而 67 道**可答题**里有 7 道（10.4%）
   的 top 分数 ≤ 22.71——阈值定在哪都会要么放过负样本、要么误杀正常问题。
   （分数只在同一配置内可比：默认配置用的是 RRF 融合分，负样本中位数 0.725，
   跨配置比绝对值没有意义，所以这个判断只在 BM25 组上做。）
   真正的拒答必须在答案链路做判定（或换成可分的信号），这条留在 `docs/priority-fixes.md` 的 P1。

**1. 强通道（BM25）几乎不受影响，弱通道（dense）被新文档成规模挤占。**

被新增的《融资担保公司监督管理条例》（**14**）以 0.70 : 0.66 挤到第 2 位——同主题新文档抢位最典型的一例；
另两道分别问"谁负责全国乡村振兴工作的统筹协调、宏观指导和监督检查"和"每年哪一天是中国农民丰收节"
（期望文档都是《乡村振兴促进法》**12**），rank-1 分别被新增的《北京市地方金融监督管理条例》（**16**）
和《中央财政农业保险保费补贴管理办法》（**15**）占据。
值得记一笔的是这几名的分数都很挤：13 份语料那一轮，这三题的前三名得分在 0.46–0.66 之间，
18 份语料这一轮是 0.48–0.70——**32 维哈希词袋本来就把这些文档排得难分难解，多进来 5 份文档就足以靠细微分差改写名次**。
**注意这不是"语料变大所以变难"，而是"新增（部分同主题）文档在弱通道上抢位"**——
BM25 在同一批题上第一名只被抢走 1 道、召回指标逐位不变，就是反证。

**2. 纯 BM25 在 v1 上反而从 0.981 升到 1.000，逐题只有 1 道题变化。**
变化的那道正是"《农村集体经济组织法》自何时起施行？"（§4 F2）：13 份语料时它排第 2、
要靠重排才提到第 1；18 份语料时纯 BM25 自己排到了第 1。数值上也对得上：
MRR 差 0.0096，恰好等于 1/52 × (1 − 1/2)——**一道题从第 2 名升到第 1 名**。
机制是 BM25 的统计量随语料变（词项文档频率与平均文档长度都变了），第 1、2 名的分差翻转。
**所以"加文档必然让指标变差"是错的假设**，方向取决于这道题的竞争格局；
同理 v1 上"重排 +1.9 pp"也不是重排的稳定能力。

**3. 随机基线自己降了，延迟升了。**
文档数变多 → 随机命中的分母变大，v1 文档级 0.246 → 0.214、v2 0.292 → 0.265
（页级 0.160 → 0.142、0.223 → 0.207）。所以"分数比随机基线高多少"这个比值变化很小，
**不要用随机基线的绝对下降说"语料变难了"**。
延迟方面 chunk 数 +22%，hybrid 组 p50 +10%～+48%（新增候选进入排序），dense 只 +10%；
延迟测量本身有 ±10% 波动（§6），这里只看量级。

### 9.5 这一节的边界

- 18 份仍是小语料：随机基线只降了 3–4 pp，"文档数增加对召回的影响"在这套数据上
  **没有被真正检验**。其中"新增文档自己能不能被检索到"这一半**已在同日补上**
  （§10：给 5 份新文档补了 20 道题，BM25 R@1 0.800）；仍然缺的是规模——18 份文档、
  20 道题的粒度是 ±1 题 = 5 pp，任何 5 pp 以内的差异都不敢下结论。
- 指标变化混着两个因素：语料变大（分母与统计量变）与干扰项变多（同主题文档竞争）。
  本轮设计无法把两者分开——要分开，得只加"同主题"或只加"异主题"文档各跑一轮。
- 数字全部可复跑：两轮的原始 JSON 都在 `docs/evaluation/` 下（13 份那轮是
  `golden-set-2026-09-27.json` / `golden-set-v2-2026-09-27.json`，18 份那轮是
  `*-corpus18-2026-09-27.json`），逐题 `per_example` 每题一行；
  "新文档占位"那组数字来自把结果里的 `document_id` 与数据库 `documents.filename` 对齐后统计。


## 10. v3 题集：给新增的 5 份文档补题

| 改动 | 为什么 |

## 11. 融合为什么没提升召回率：把机制数出来，并给出可复现的修法

### 11.1 先看口径：本节取代 §9/§10 里的融合行

§9、§10 的融合行写在**修复前**的产物上，而那时的平局胜负由一个每次导入都会变的东西决定
（见 11.4）。纯 BM25 与 dense 行不受影响（它们不产生跨文档平局），但融合行请以本节为准：
v3 的等权 RRF 由此前的 0.550 变为 **0.600**，v2 由 0.512 变为 **0.527**，v1 不变（0.904）。

本轮把配置矩阵从 6 组扩到 11 组，在同一份 18 文档 / 386 chunk 语料上重跑三套题集，并加了一条
**可复现性检查**：v3 用两个独立数据库各跑一遍，11 组配置的质量指标逐位相同（延迟 p50 波动
8%–9%，延迟本来就会动）。下面每个数字都能在
`docs/evaluation/golden-set-{v1,v2,v3}-fusion-2026-09-28.json` 里逐条对回。

### 11.2 机制：页级探针数出"谁把谁的冠军挤掉了"

`scripts/probe_fusion.py` 走产品路径（每个通道各取 20 个候选再融合，与 `HybridRetriever` 逐字
等价；不是直接调 `retrieve()` 拿全量排序——那样会把长尾的影响算大）。对每道单跳题统计：
纯 BM25 是否把标注页排在第一、融合后是否还在第一、融合救回了谁。

| 融合方式 | BM25 页级第一 | 融合后仍第一 | 被挤掉 | 掉出 top-5 | 救回 |
|---|---|---|---|---|---|
| **v2：52 道单跳题** | | | | | |
| 等权 RRF | 35 | 16 | 19 | 6 | 2 |
| 加权 RRF（0.3 / 0.7） | 35 | 20 | 15 | 6 | 1 |
| 截断 RRF（各通道 top-5） | 35 | 22 | 13 | 0 | 2 |
| convex（等权） | 35 | 22 | 13 | 0 | 2 |
| convex 加权 | 35 | **34** | **1** | 0 | 0 |
| **v3：20 道单跳题** | | | | | |
| 等权 RRF | 16 | 8 | 8 | 3 | 2 |
| 加权 RRF（0.3 / 0.7） | 16 | 10 | 6 | 3 | 0 |
| 截断 RRF（各通道 top-5） | 16 | 8 | 8 | 0 | 1 |
| convex（等权） | 16 | 12 | 4 | 0 | 1 |
| convex 加权 | 16 | **15** | **1** | 0 | 1 |

对照：**同一批题上 dense 通道单独的页级第一只有 7/52（v2）与 2/20（v3）**，而纯 BM25 是
35/52 与 16/20。三条机制，逐条都有数字：

1. **等权把弱通道当成同等可信的独立证据。** dense 单独的正确率是 13% / 10%，BM25 是 67% / 80%，
   RRF 让两者各投一票：v2 上它用"挤掉 19 道"换"救回 2 道"，净负 17 道。
2. **RRF 只用名次、丢掉分数幅度。** 于是某个通道的第 200 名与第 1 名在公式里只差 `1/(60+200)`
   与 `1/61`；候选不截断时，长尾也在投票。截断把"掉出 top-5"从 6 压到 0，但**没把文档级 R@1
   救回来**（v2 0.527 → 0.537）——说明损失不止来自长尾。
3. **两个通道的错误不独立。** `HashEmbedding` 是 32 维 sha256 符号哈希，没有 idf、没有长度归一，
   和 sparse 通道吃的是同一批字符 n-gram，于是它们在"看着像但答非所问"的段落上同时犯错。
   加权只能改投票权重，改不了这种相关性（v2 的"被挤掉"从 19 降到 15，仍远高于 convex 加权后的 1）。

### 11.3 四种修法：哪种真的把召回拿回来了

同一份语料、同一套题，11 组配置的文档级 R@1 / page_hit：

| 融合方式 | v1（52 题） | v2（75 题） | v3（20 题） |
|---|---|---|---|
| 纯 BM25（上界） | 1.000 / 1.000 | 0.660 / 0.851 | 0.800 / 0.900 |
| 纯 dense（弱通道） | 0.673 / 0.769 | 0.276 / 0.328 | 0.300 / 0.300 |
| **等权 RRF（原实现）** | 0.904 / 0.904 | 0.527 / 0.657 | 0.600 / 0.750 |
| 加权 RRF（BM25 0.7 / dense 0.3） | 0.942 / 0.923 | 0.581 / 0.687 | 0.650 / 0.750 |
| 截断 RRF（各通道只取 top-5） | 0.923 / 0.981 | 0.537 / 0.821 | 0.500 / 0.850 |
| convex（逐通道归一化分数，等权） | 0.923 / 0.981 | 0.557 / 0.836 | 0.700 / 0.900 |
| **convex 加权（BM25 0.7）** | 1.000 / 1.000 | 0.646 / 0.866 | 0.850 / 0.950 |
| convex 加权 + 重排（本地词面重排） | 1.000 / 1.000 | 0.646 / 0.866 | 0.850 / 0.950 |
| 等权 RRF + 重排 | 0.942 / 0.923 | 0.546 / 0.687 | 0.650 / 0.750 |

读法（"题数"一律指单跳题，v1 是 52 题全为单跳，v2 的单跳子集 52 题，v3 的 20 题）：

- **只加权**：v2 0.527 → 0.581、v3 0.600 → 0.650。好转，但离纯 BM25 仍远。
- **只截断**：page_hit 明显变好（v2 0.657 → 0.821、v3 0.750 → 0.850），R@1 几乎没动
  （v2 0.537、v3 0.500）。它治的是长尾投票，不是冠军被错顶。
- **只换成分数式（convex）**：v2 0.557、v3 0.700，page_hit 0.836 / 0.900。
  **分数幅度才是主要缺失项**，只补权重不够。
- **分数 + 加权**：v3 上**首次超过纯 BM25**（R@1 0.850 vs 0.800、page 0.950 vs 0.900；
  单跳题数 17/20 vs 16/20、19/20 vs 18/20）；v1 上与纯 BM25 同为满分；
  v2 上仍差 **1 道题**（单跳 37/52 vs 38/52），不过 page_hit 反而更高（0.866 vs 0.851）。
- **本地词面重排**：加在任何融合上都改不动文档级 R@1，只动最细粒度——convex 加权 + 重排把
  v2 的 passage@1 从 0.582 抬到 0.597（39/67 → 40/67）、v1 从 0.712 抬到 0.750（37/52 → 39/52），
  文档级指标一个都没动。这与 §9"候选变多时重排才有用"同源；真正的差别要等 §11.5 换成语义重排
  才看得到（v2 的 R@1 0.646 → 0.769）。
- **代价**：融合把 p50 从 0.86s 抬到 1.21s（v2，同语料同题集、缓存关闭），最好的结果是打平。
  纯 BM25 在这个语料上又快又稳，这也是它一直没被换掉的原因。

所以对"为什么没提升还下降了"的完整回答是：**等权投票 + 只用名次丢分数 + 弱通道的错误与强通道
高度相关**。前两条能用加权与分数式融合修掉（v3 上已经修到超过纯 BM25），第三条只能换通道——
11.5 的语义重排就是针对它的尝试。

### 11.4 一个必须记下来的缺陷：平局曾由"导入顺序"决定

`Chunk.id` 是 `f"{document_id}:{index}"`，`document_id` 每次导入重新生成的 UUID，而
`store.get_chunks` 是 `order_by(ChunkRecord.id)` 返回——于是：

- 旧实现的平局胜负 = "谁先出现在 dense 列表里" = **由导入顺序决定**；
- 我第一版修法用 `chunk_id` 破平 = **由随机 UUID 决定**，同样不可复现。

证据：同一份语料、同一套 v3 题集、只差平局规则/导入顺序，`hybrid-rrf` 的 R@1 跑出过
**0.550 与 0.700** 两个值——而"规则变化"和"导入顺序变化"的影响事后无法拆分。这类题目
（多个近似条款都能回答的定义题）在 v2 里一次就出现了 4 道排序位移。

修法：破平只用**内容**——`(-分数, 最好名次, page, 正文)`，并加一条测试把两名平局候选的
`id` 前后调换，要求内容顺序不变（RED 验证：把键改回 id 立刻变红）。产物侧的可复现性检查
（11.1）证明修复有效。代价是：**所有融合类的历史数字都带这个不确定性，本轮为此全量重跑**。

### 11.5 换掉弱通道：接一个真语义通道（TypeSafe / Jev）

前两条机制能靠融合公式修，第三条（弱通道的错误与强通道相关）修不了，只能换通道。这一节把
TypeSafe 的 Jev 接成**可选**重排后端（`RERANK_BACKEND=typesafe`，默认仍是本地词面重排），
沿用官方 rerank cookbook 的形态：**一个候选一次请求**（`state = {query_excerpt, candidate_passage}`，
`questions` 里一个 `type: noul` 判断题，取返回概率排序），8 路并发、429 按 `retry-after` 退避。

它不是免费的：按输入 token 计费（$42/Btok，输出免费），而且**候选正文会发到第三方**。
所以它不进离线矩阵，单独跑，并且产物里自带用量与花费：

| 题集 | 调用 | 输入 token | 实测花费 | 每查询 p50 |
|---|---|---|---|---|
| v3（20 题） | 400/400 | 427,239 | **$0.0179** | 1.23s → **3.03s** |
| v2（75 题） | 1500/1500 | 1,659,530 | **$0.0697** | 1.27s → **3.09s** |

产物里的 `rerank_usage` 同时记 `expected_calls` 与 `degraded`——因为失败会静默回退到本地词面
重排，而回退**不发请求**，靠"实际调用数 == 题数 × 候选数"才能证明这批数字真的来自语义通道
（两轮都是 1500/1500 与 400/400，`degraded=false`）。

| 配置 | v3 R@1 / page / passage@1 | v2 R@1 / page / passage@1 |
|---|---|---|
| 纯 BM25 | 0.800 / 0.900 / 0.700 | 0.660 / 0.851 / 0.612 |
| convex 加权（+本地词面重排） | 0.850 / 0.950 / 0.700 | 0.646 / 0.866 / 0.582 |
| **convex 加权 + TypeSafe 重排** | **0.950 / 1.000 / 0.950** | **0.769 / 0.896 / 0.716** |

单跳题的直接读数：v2 是 **37/52 → 45/52**（纯 BM25 38/52，page 45/52 → 47/52），
v3 是 17/20 → 19/20（page 19/20 → 20/20）。**这是本报告里第一组在难集上明确超过纯 BM25 的配置**，
而且超过的不止文档级：v2 的 passage@1 从 0.582 到 0.716，同时高于纯 BM25 的 0.612。

逐题得失（v2，相对本地词面重排）：**10 道变好、2 道变差**。变好的集中在"银行按什么定还款期限"
"小额贷款公司股东最少交多少钱"这类**词面相似但语义不同**的问法；变差的是两道语义上更弥散的题
（同一借款人贷款余额上限、等价多标签的"这些规定由谁负责解释"）。按类别看更清楚：

| 类别 | 题数 | convex 加权 R@1 | +TypeSafe R@1 |
|---|---|---|---|
| 同义改写（单跳） | 52 | 0.712 | **0.865** |
| 等价多标签 | 6 | 0.292 | 0.333 |
| 多跳 | 9 | 0.500 | 0.500 |

**多跳一道没涨**。这不是重排的问题，而是**重排改变不了候选集**：多跳题失败在"正确的第二个
文档根本没进 20 个候选"，而重排只能在给定候选里排序（与 §9、§11.3 里"候选变多时重排才有用"
是同一条规律的另一面）。要把多跳也提上去，得先提高召回（更强的检索通道或更大的候选窗口），
不是更强的排序器。

**能说的**：在自建中文法规题集上，把弱通道换成真语义通道后，难集 R@1 0.646 → 0.769（单跳
37/52 → 45/52），同时 page/passage 指标都超过纯 BM25；代价是每查询 +1.8s 与约 $0.07/1500 次调用；
失败会静默降级，所以产物必须自证调用次数。
**不能说的**：这不是"我的系统在 1 万 chunk 上的表现"（386 chunk、75 题）；也不能说语义重排
"普遍提升召回"（多跳 0.500 → 0.500 一道没涨，且有 2 道变差）；更不能把它当成默认能力——
它默认关闭，因为它是付费调用且会把候选正文发到第三方。

### 11.6 这一节的边界：能写与不能写

**能写**：定位到等权/名次/相关性三处机制并用探针量化（被挤掉 19 道 vs 救回 2 道）；实现四种
融合变体做对照；发现并修复"平局由导入顺序决定"的不可复现缺陷，并加可复现性回归；用内容破平
+ 分数式加权把 v3 的混合检索做到**超过**纯 BM25；给出每种修法的代价（p50 +40%、最细粒度指标
仍低于纯 BM25）。

**不能写**："混合检索提升召回率"（v2 上仍差 1 道单跳题：37/52 vs 38/52；最细粒度的 passage@1
也仍低于纯 BM25，v2 是 39/67 vs 41/67、v1 是 37/52 vs 40/52）；
"加权融合是最好的方案"（它只是把等权丢掉的召回拿回来，v1 上是打平而非提升）；
"语义通道已经在用"（11.5 的 TypeSafe 是可选后端，默认关闭）。
